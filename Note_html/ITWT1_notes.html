The web is fundamentally built on a client-server paradigm: the client is the browser side (Module 3 teaches you to program it), while the server side is where the data lives and the backend logic runs (Module 5). Module 4 sits between the two, introducing the MVC (Model-View-Controller) architecture — the standard set of layers used to organize how frontend and backend interact. Module 6 then covers how the client and server actually talk to each other in a structured way, using REST APIs. By Module 9, the goal is that the theoretical and programming aspects covered throughout the course converge into the practical skill of building and deploying your own end-to-end web application.

What Happens When a Webpage Loads

You've probably noticed that some pages load almost instantly, while others render in bits and pieces — text first, then images, then styling snapping into place. This happens because the content your browser fetches is never local to your system — it has to travel, often across multiple networks, before it reaches you.

Walking through the flow:

  1. Type the URL — You open a browser (Chrome, Brave, Edge — pick your poison) and type an address, e.g., the CSE department page at IIT Jodhpur, then press Enter.
  2. Check Local Cache — The browser first checks whether it already has this page cached. Caching exists purely for performance: if you've visited the page recently, there's no need to burn bandwidth fetching it again.
  3. DNS Resolution — If it's not cached, the browser needs to find where the content actually lives. DNS (Domain Name System) converts a human-friendly name like iitj.ac.in into the corresponding IP address, because the routers that carry your request only understand IP addresses, not names.
  4. Connect Securely — Security protocols establish the end-to-end connection (the TCP handshake, followed by TLS for HTTPS).
  5. Route Across the Internet — The request packets hop through multiple routers to reach the destination server.
  6. Server Handles Request — The server is rarely dedicated to just one page; it often hosts many websites and services, and may talk to other backend servers before responding — using a protocol that is part of HTTP.
  7. Response Routes Back — The response may take a different path back than the request took, but it follows the same routing principles across multiple networks until it reaches your local network.
  8. Fetch Linked Resources — The browser requests any additional resources the page references (CSS, JS, images, fonts).
  9. Render the Page — Finally, the content is rendered in your browser, and you see what you asked for.

All of this typically happens within a split second on a robust connection — but on a weaker one, you'll notice the page loading in visible stages.

What Is the Internet?

At the simplest level, when two devices — say a phone (X) and a laptop (Y) — run the same application (e.g., a WhatsApp Web chat) and communicate with each other, "the Internet" is the abstraction sitting between them: a cloud that just works.

But underneath that abstraction, there's a lot going on, and understanding it in some detail makes it much easier to talk about the rest of this course.

The Internet is, fundamentally, a network of networks.

It's made up of many different underlying network technologies — cellular (4G/5G), Wi-Fi (home networks), Ethernet (enterprise networks), and datacenter networks in the cloud. All of this infrastructure exists to connect hosts (end devices): smartphones, laptops, connected vehicles, wearables, and so on.

  • Network edge — the hosts/devices and access points at the boundary of the network.
  • Network core — the servers and infrastructure ("network of networks") that provide the actual connectivity backbone.

To bridge the heterogeneity of all these different device and network types, everyone follows shared protocols — standardized rules for communication, such as HTTP, TCP, and IP. Protocols are what let a phone on 4G talk to a server on Ethernet without either side needing to know the details of the other's hardware.

Internet Structure — Building the Network of Networks

Hosts connect to the Internet via access ISPs (Internet Service Providers) — the entities that build, maintain, and manage the actual physical infrastructure carrying packets between hosts.

The scaling problem: if every access ISP tried to connect directly to every other access ISP (a mesh/"click" structure), you'd need on the order of O(N2) connections — completely infeasible as the network grows, even though any host still needs to be able to reach any other host.

Attempt 1 — One global transit ISP: connect every access ISP to a single global ISP, under a customer–provider economic relationship (you pay the global ISP to carry your traffic to another access network). This solves the scaling problem, but a single global ISP isn't feasible either — coverage of the entire globe, business-model concerns, and scalability all break down.

Attempt 2 — Multiple competing ISPs: since one global ISP isn't feasible, multiple ISPs (ISP A, ISP B, ISP C, ...) each build out their own regional backbones, with access ISPs connecting to whichever provider serves them.

Attempt 3 — Peering and content providers: these regional ISPs then interconnect with each other at Internet Exchange Points (IXPs), and via direct peering links. Meanwhile, large content provider networks (Google, Microsoft, Akamai, Facebook) build their own private networks to bring content physically closer to end users, often bypassing tier-1 and regional ISPs entirely.

The final, real-world structure is a hierarchy: at the "center" there is a small number of well-connected large networks —

  • Tier-1 commercial ISPs (e.g., Level 3, Sprint, AT&T, NTT) providing national and international coverage.
  • Content provider networks (e.g., Google, Facebook) — private networks connecting their own data centers to the Internet, often bypassing tier-1 and regional ISPs.

Below that sit regional ISPs, and below those, the access ISPs that individual hosts connect through. This entire structure is not centrally designed — it's an emergent, evolving system shaped by economics, national policy, and business relationships between providers (who peers with whom, who pays whom).

Worked example — packet path: Suppose host X is on one access network and host Y is on another, geographically distant one. X's device sends a packet over a wireless channel to its local Wi-Fi access point, which connects to a layer 2 device (a switch) managing local network functions — handling things like fading, multipath effects, and interference on the shared wireless channel. From there, the packet is forwarded up to a layer 3 device (a router), which makes the actual routing/forwarding decision — this is the essence of routing protocols. The packet then hops across multiple routers, eventually reaching a router in Y's access network, and finally Y's local base station/access point delivers it to Y's device.

Note for Review: The distinction between a layer 2 device (switch) and a layer 3 device (router) is a favorite exam point. A switch only needs to operate up to the Data Link layer to forward frames within a local network; a router operates up to the Network layer because its job — routing and forwarding across different networks — genuinely requires network-layer (IP) information.

Host-to-Host Communication over the Internet

Now zoom into what happens inside each host when it sends or receives data, using the standard TCP/IP protocol stack:

Walking down and back up the stack:

  • Application layer — Suppose the same application process (say a web browser) runs on both X and Y; this is where application data is generated.
  • Transport layer — The generated data is divided into chunks and handed to the transport layer, which establishes an end-to-end (virtual) connection — for example, a TCP connection acts like a secure virtual tunnel, even though physically the packets are just a stream of 0s and 1s traveling over wires or radio.
  • Network layer — Handled by the host's NIC (network interface card); this is where routing/forwarding logic lives.
  • Data Link layer — Manages how multiple hosts sharing the same channel (e.g., several devices on the same Wi-Fi) cooperate and compete for bandwidth — this is where flow control and error control happen. Protocols like ARP/RARP operate here.
  • Physical layer — The actual transmission medium: radio channel for wireless, or coaxial/copper cable for Ethernet — the literal 0s and 1s moving through hardware.

A layer 2 device (like a switch) only needs to operate up through the Data Link layer, since its job is simply to connect hosts within a local segment — it has no need for network-layer services. A layer 3 device (a router) operates up through the Network layer, since its job is to perform routing and forwarding, connecting to many other routers to form the core of the network.

The packet's journey: Application → Transport → Network → Data Link → Physical on the sending host, across potentially many layer-2 and layer-3 devices (routers), and then back up through Physical → Data Link → Network → Transport → Application on the receiving host. At the transport layer on the receiving end, the packet must be matched to the correct process (since a host runs many processes simultaneously) before the application data is finally delivered.

The Web: Client, Server, and How They Talk

The web is a specific application built on top of the Internet's connectivity infrastructure, structured around a client and a server that may be geographically far apart.

  • The web client is typically a web browser — the side that initiates requests.
  • The web server hosts multiple documents. A website is a collection of interlinked pages you can navigate across.
  • HTTP (HyperText Transfer Protocol) is an application-layer protocol that relies on the transport-layer protocol TCP and the network-layer protocol IP. Together, these three layers support the web: the client sends a request to the server, and the server sends back a response containing the requested resources, which the browser then renders.

Basic Architecture of the Web — A Worked Example

Consider visiting the IIT Jodhpur CSE department page. Breaking apart the URL (Uniform Resource Locator):

https://iitj.ac.in/computer-science-engineering/
  • https — the protocol (secure HTTP)
  • iitj.ac.in — the domain name (address of the host server)
  • /computer-science-engineering/ — the path, locating a specific page hosted on that server

A URL therefore encodes two things: which server to reach, and which specific page on that server to fetch.

When this page loads, several things happen behind the scenes, each involving a separate client-server exchange:

  1. The browser sends a GET request (one of HTTP's request methods, used to fetch data) for the page — e.g., the index HTML — from the web server at iitj.ac.in.
  2. Simultaneously, the page might send a request to google-analytics.com, a completely different server, to log/report visit rankings and analytics.
  3. If the page embeds a YouTube video, clicking on it triggers a request to YouTube's servers, which may in turn query a database for the actual media/document, before sending it back.

In every one of these cases, the pattern is the same: the client (browser) always initiates the request; the server always responds with data. The server's response — a static or dynamic web page, typically built with HTML, CSS, and JavaScript — is then rendered by the browser for the user to see.

Note for Review: "Static vs. dynamic" is a key distinction this module sets up for later: a static page is the same HTML sent to every visitor, while a dynamic page is generated (often per-request, often from a database) on the server before being sent. We'll unpack this further along with HTTP methods in upcoming sessions.

Process-to-Process Communication

Zooming in one more level: communication over the Internet isn't really host-to-host — it's process-to-process. A process sends and receives messages through its socket.

A helpful analogy: a socket is like a door.

  • The sending process shoves its message out through the door (the socket).
  • It then relies entirely on the transport infrastructure on the other side of the door to carry the message to the socket at the receiving process.
  • Every communication involves two sockets — one on each side.

Two different parties are responsible for two different sides of this picture:

  • The application process and its socket are controlled by the app developer — this is the code you actually write.
  • Everything below the socket (transport, network, link, physical) is controlled by the operating system.

Note for Review: This client/OS split is worth remembering — as an application developer, your entire job is to correctly open, write to, and read from a socket. You never have to personally implement TCP's handshake or IP's routing; the OS and network stack handle all of that beneath the socket abstraction.
